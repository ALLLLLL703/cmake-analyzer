# Agent Instructions

## Provenance Labels

- Directly AI-authored Markdown must include `> AI-generated content.` near the top, after any required front matter.
- Directly AI-authored tests must include a language-appropriate header, such as `// AI-generated tests.` for Rust.
- Script-generated files must be labeled as script-generated, not AI-generated, even when an AI wrote the generator. Identify the generator path, for example `// Script-generated by scripts/gen/example.rs.` or `> Script-generated content. Generator: scripts/gen/example.py`.
- The generator itself is authored code, not a script-generated output. Apply the relevant authorship rules to it.
- When modifying human-authored or mixed-authorship Markdown or tests, mark the AI-authored additions or edits explicitly. Use a file header such as `> Contains AI-generated additions or edits.` or `// Contains AI-generated tests or test edits.` when changes span the file; use adjacent comments when attribution can be localized.
- Preserve accurate existing provenance labels. Correct an inaccurate AI-generated label on a script-generated output to a script-generated label.
- For manual AI edits to script-generated files, retain the script-generated label and mark the AI-authored edits separately. Do not relabel the whole file as AI-generated.
- Do not describe unmodified human-authored content as AI-generated.
- These requirements also apply to test helpers, test-module scaffolding, documentation, and this file itself.
- Before finishing, verify that generated outputs and created or modified Markdown/tests carry the appropriate script-generation or authorship labels.
- Keep Markdown content in English.

## Design Requests

- Prefer existing dependencies.
- For technical proposals, flag concrete rule, performance, or readability problems and offer better alternatives.

- Decline requests that conflict with project code rules or clearly impose unjustified performance costs or reduce readability. Explain the concrete problem respectfully and offer a better alternative.
- For viable requests with design flaws or meaningful trade-offs, use the question tool to agree on a better approach rather than rejecting or silently changing the design.

## Source and Generator Locations

- Reserve `target/` for Cargo-managed build artifacts. Do not place source code there, including temporary code, smoke-test sources, helper projects, scripts, or generated source files.
- Keep code-generation scripts and generator projects under `scripts/gen/`, not `target/`.
- Write generated project sources to their intended source directories. Temporary verification sources must also stay outside `target/`.

## Writing and Checks

- Keep Markdown and comments terse.
- Document non-obvious APIs; explain obscure logic inline. Short, clear functions need no comments.
- Apply this to new and edited code.
- Installed `.cmake` files under `/usr/lib/cmake` may be used as read-only test inputs.

## Small Changes

- For small, localized fixes, edit only the relevant files. Tests and updates to `agent-instructions/Architect.md` are not required unless explicitly requested.
- This exception does not apply to architecture changes.

## Architecture Record

- Maintain `agent-instructions/Architect.md` as the project architecture record, including relevant files, responsibilities, key functions, and implementation limits.
- On agent initialization and after every architecture change, inspect the current source and create or update this record. Keep it consistent with implemented behavior, not planned features.
- The coding agent is responsible for this maintenance. Follow the Markdown provenance and English-language rules above.
